# 相机长期缓存与两分钟即时回放

更新项目后，继续从项目根目录运行：

```bash
python3 PyScripts/Camera_mit_Rotation_dashboard.py
```

无需修改接线、重新烧录 ESP32 或安装 FFmpeg。刷新网页，找到相机画面下方的“相机即时回放”。

## 操作

1. 开启需要的相机，确认画面正常。
2. 选择回放录制帧率，默认 **60fps**，然后点击“开启两分钟回放”。此时才开始缓存，不能找回开启前的画面。
3. 保持后台运行；关闭网页不停止后台缓存。程序持续覆盖旧片段，内存不随录制时间增加。
4. 需要保留一次试验时点击“保存最近两分钟”。窗口以后台收到该请求的时刻结束，不等待之后两分钟，不包含之后的画面。两路相机使用同一主机单调时间截止点。
5. 保存完成后下载 AVI、逐帧 CSV 和 manifest；后台继续缓存，可以再次保存。上一段保存完成后才能开始下一次保存。
6. 点击“停止回放缓存”停止加入新画面；已缓存画面在最近两分钟范围内仍可保存，随后自动过期。再次开启会保留尚未过期的历史，关闭相机也会停止该路缓存。增加相机后需重新开关回放以纳入该路。

未积满两分钟时保存已有画面。界面显示各相机的缓存时间跨度、容量、目标帧率和丢帧数；导出结果显示实际帧数与时间跨度。没有新画面时跨度不代表实时就绪，过期帧不参与导出。中途停止或丢帧造成的时间空缺不会被补造。

## 文件

默认输出（可通过现有 `CAR_RECORDS_DIR` 改保存根目录）：

```text
Car_Records/
  .camera_replay_cache/Left或Right/唯一缓存目录/    # 临时分段
  Replays/日期_时间_微秒/
    Left.avi / Right.avi                       # 可独立播放的 MJPEG 视频
    Left.index.csv / Right.index.csv           # 每个视频帧的原始主机时间
    manifest.json                              # 请求窗口、实际覆盖、丢帧与错误
```

缓存片段约两秒一个，保留最近 120 秒；默认每路缓存容量上限 **1GiB**。容量先到上限时丢弃最旧片段，实际历史可能少于两分钟，网页会提示。正在写的片段和导出期间被保护的源片段可以暂时超过该限额。已有导出录像不会自动删除，每次保存也需要额外磁盘空间。

后台正常退出时释放未保存的临时缓存；断电或强制结束可能留下之前进程的 UUID 缓存目录，重启不会将其当成当前缓存。应在确认相关后台已关闭后清理残留临时目录。已保存的 `Replays` 文件夹独立保留。磁盘空闲不足 128MiB 时停止缓存并报告错误；写盘失败后需处理存储问题、重启后台并重新开启回放。

## 性能与时间

- 回放复用现有相机采集线程，不再次打开 `/dev/video*`。相机采集仍请求原来的 640×480、210fps；**回放存储默认抽帧到 60fps**，可选 1～240fps，不能超过相机实际出帧能力。改变帧率需先停止回放。
- 采用 MJPEG，利用项目已有 OpenCV 编码 JPEG，分段写入 AVI。导出时复制压缩数据，不对两分钟录像二次编码。这里实现的是即时回放功能，未使用 NVIDIA NVENC，也未启用 Orange Pi 硬件 H.264/H.265 编码；MJPEG 文件比这些格式大。
- 写盘队列默认每路 16 帧；忙时跳帧并统计，避免无限积压原始图像。目标抽帧不计为丢帧，编码/磁盘负载造成的队列溢出和锁竞争跳帧分别统计。普通三秒多源记录也改为边采边写的有界队列，继续输出原有 JPG 和匹配 CSV，同时增加 `frames.index.csv`、`recording.json`。
- 60fps 是初始目标，不是本机或 Orange Pi 的性能保证。先观察实际帧率、丢帧和磁盘空间；两路相机、网页预览、普通图片记录同时运行会增加负载，必要时降至 30fps。
- `host_receive_monotonic_ns` 为 OpenCV 读帧完成后取得的主机单调时间，`host_receive_unix_ns` 为同一帧的主机墙上时间；均不是曝光时间，也不代表纳秒精度。`frame_id` 可以检查抽帧/丢帧后的原采集序号。
- AVI 使用实际保留帧的平均帧率；长间隔或不规则掉帧在播放器里不能精确还原。分析及同步时使用逐帧 CSV 的真实时间，不以播放器帧率推算所有帧的时间。
- 回放保存 **相机视频与索引**。若需回看时同时有车速和压力数据，必须在试验前启动现有车速＋扫描阀同步记录，保持其覆盖该时间段。录像不会补回未记录的传感器数据，也未把两类文件自动裁剪成同一个批次。

## 速度到底保存多少 Hz

正常固件 `serial_transport.cpp` 每 10ms 尝试发送一条 `[ENC]`，因此目标约 **100Hz**。后台收到有效帧就送入 CSV 写盘队列，网页曲线刷新频率不会降低原始保存频率。`L/G/V/M/O` 调试模式暂停编码器输出，不能用于同时记录车速。

速度记录状态现在显示 `saved_hz`，按已写入的首末两条数据的主机单调时间计算 `(样本数−1)/时间跨度`，这是该批次的平均实际保存频率；数据太少时显示等待。原有缺样和写盘丢样统计保留。速度算法的约 100ms 计算窗口及 EMA 滤波会影响速度响应延迟，不把 CSV 保存频率变成 10Hz。
